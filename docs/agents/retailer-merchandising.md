# Retailer collections and home merchandising

The connected retailer renderer accepts the optional `shopping-storefront-content-v1`
export generated by `environments.product_world.storefront_content`. Generation owns
collection membership, sampled sections and evidence for commercial claims. Rendering
owns navigation, grouping, routes and presentation. Existing publications stay frozen.

## Public contract

Pass `storefront_content` in the scenario or explicitly to `Runtime`. It is validated
against the canonical world and initial accounts before servers start. The unchanged
export is available as `rt.storefront_content`, with `storefront_content_sha256` and
version in provenance. The preview CLI saves `storefront-content.public.json`; an
explicit override is available through `--storefront-content FILE`. Task binding must
use that same hash. Merchandising never changes the task, prices, stock or quotes.

Collection rules use product attributes, with complete carried SKU membership. A shoe
specialist can therefore expose walking/running/hiking/dress shoes and flip-flops instead
of a single Footwear department. Actual available categories depend on the draw.
Other supported families use their typed facets; multi-family stores can also have
broad departments. Search supports `collection=ID`, and category search remains valid.

Sections are featured picks, new arrivals, bestsellers, editorial collections or
promotion spotlights. Introduction dates and model-level sales metadata support new
and bestseller claims. Promotions do not invent discounts, delivery offers or private
coupons. The renderer displays at most four cards per home section; the section page
exposes its full declared membership. Footwear cards group carried sizes by model and
use the minimum carried option price; exact size, colour, price and stock remain on the
product page. No task winner or availability preference determines home placement.

## Generation and sampling

```python
from environments.product_world.storefront_content import attach_storefront_content
scenario = attach_storefront_content(scenario, seed=42)
```

Attachment deep-copies the scenario and adds only `storefront_content`. The snapshot
date defaults to the initial accounts date, otherwise the merchant-review snapshot.
For standalone use, `generate_storefront_content(world, seed=42, as_of=...,
accounts=initial_accounts, config=...)` returns the sidecar;
`validate_storefront_content(world, sidecar, accounts=initial_accounts)` checks it.
World and initial-account hashes bind its scope. No task or winner enters sampling.

Defaults draw two or three distinct section kinds with equal count weights and equal
kind weights. `section_count_weights` and `section_kind_weights` override those priors;
`products_per_section` defaults to four, with a maximum of eight. Small inventories
cap section counts; absent new arrivals or zero sales cannot support those sections.
Impossible pools remain empty instead of triggering a new world draw.

Collections are derived from complete carried membership, regardless of current stock.
Footwear uses `shoe_type`, with `activity` as the legacy fallback. Other current facets
are laptop RAM, beer style, wine colour and pet-food life stage. Broad departments appear
only where the actual carried catalog spans multiple families. A section uses at most
one representative SKU per model, while collections retain every carried variant.

Newness is sampled with `new_arrival_probability` (0.3), `new_arrival_days` (30), and
`maximum_age_days` (365). The window includes today and the previous 29 days by default.
An introduction date cannot postdate any known historical order at that retailer,
including cancelled orders. Historical evidence can therefore reduce the realized
new-arrival rate. Sales sampling scales with the merchant business profile and the
model's time on sale; `sales_multiplier` defaults to 1. Counts cannot fall below known
noncancelled account order units in the same 30-day window. Competition ranks count
models with strictly greater sales, so tied models have equal ranks.

These are synthetic metadata at the initial world snapshot. Runtime cancellations do
not rewrite merchandising history. The export declares the window, basis and excluded
cancelled orders; it contains no order IDs or coupon codes. Validators reject unsupported
claims, chronology conflicts, incomplete collection membership, repeated models and
ranking errors. Price-affecting campaigns remain outside this contract.

`Episode.from_runtime` verifies the raw sidecar and provenance hash. Episode identity
includes merchandising when present; public task requirements and the exhaustive price
reference remain unchanged. Legacy episodes without the sidecar keep their identity.

## Layout and routes

- `/collections/ID`: complete collection, twelve model/configuration cards per page.
- `/highlights/ID`: sampled home section, with pagination if necessary.
- `/search?q=...&collection=ID`: search within the declared collection.
- `/returns`, `/terms`, `/contact`: compact own-site information pages.

Boutique navigation is a horizontal collection list. Dense stores use an expandable
category menu. Technical catalogs put categories in their sidebar. These are optional
catalog fields in the existing layout shells; legacy commerce pages retain their
original defaults when the sidecar is absent. Customer-service navigation is compact,
including on boutiques. Unknown return terms/contact details are stated as unavailable;
there are no invented return promises, support endpoints or transaction capabilities.

Native forms and links work under the existing no-script CSP. Retailers still have no
shortcut links to the web index, aggregators or independent reviews. This publication
remains research-only for purchasing; existing account and quote capabilities are intact.

## Validation

`test_storefront.py` checks declaration-to-page navigation, collection isolation,
model price grouping, service routes, malformed bindings and canonical-world preservation.
`verify_storefront_merchandising.py --pin PIN --output NEW` runs three isolated native
browser journeys in parallel with two workers, recording actual harness AX projections
and screenshots. It checks category navigation, collection-scoped search, exact SKU
selection, section links and footer routes. It makes no model calls.

The connected-world conformance audit additionally checks the raw sidecar/hash, each
retailer home, every collection page and declared product membership, alongside existing
product/variant/quote/review checks. HTTP conformance and scripted browser acceptance
are separate from model-performance evidence.
