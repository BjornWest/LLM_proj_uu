# Keyboards — neutral family authoring foundation

Status: prose draft before DSL, 2026-10-01. Proposed `_keyboards_base.json`, owned
by lane A for current `keyboards.desktop_keyboards`. This support is not a counted
concept. No JSON base or child exists at this prose gate.

Reuse the read-only electronics identity and independent profile semantics:
explicit brand/model identity, brand-supplied positioning weights and execution
uniform0.05–0.95. A keyboard family foundation supplies no battery, connection,
format, switch, backlight, dimensions, mass, language manufacture, key count,
software compatibility, price bands or owner topics by default. Children author
those facts and replace any inherited manufacture/price producers explicitly.
Old electronics/charger/pilot sources, shared compiler and consumer sites remain
unchanged.

Canonical child rows retain `sku_id`, owning `product_id`, cosmetic colour,
`language_layout` and exact synthetic SEK reference. Only declared retail axes
may become selectors or page partitions; extra row facts such as key count,
physical layout, lead status and reference price remain canonical even when they
are description-only. Retail stock/carried subsets follow manufacture and cannot
invent variants or replace row facts. No shared-language name implies common
geometry, key counts, printed symbols, firmware map or regional availability.

Reference price bands and any multipliers are child-owned, anchored before
subset sampling; independent reviews bind the actual selected canonical row and
explicit reference-price bounds. Preserve concentration1.5,75% silent comments,
variable topic selection/order, protected value frequency and modest cheap-price
sentiment adjustment at fixed satisfaction. Private execution is generation input,
never publicly available evidence of comfort, reliability or latency. Source
examples establish plausible distinctions, not palette/recipe probabilities.
